**Honest summary:** no open project found does the offline Cartesian → XZC conversion with exact joint-space error
control, segmented rapids, several pole strategies and a replay/sweep test suite. Firmwares use fixed or time-based
segment lengths.

### Methods in our own words
- **Centre offset (Marlin idea):** if the cutter's line of travel passes the chuck axis at a distance e (height error of
  the router), a point at radius r and angle θ is reached with X = √(r² − e²), C = θ − atan2(e, X) (sign by side).
  Radii below |e| cannot be reached at all — they leave a **centre pin of radius e**. Without compensation the part is
  slightly distorted near the centre and that pin stays.
- **Pole speed (Klipper idea):** for a move whose straight Cartesian line passes at d_min from the centre, the chuck
  needs ω = v / d_min; with ω limited, the true feed there is at most ω_max·d_min. Useful for **time estimates and
  warnings only** — LinuxCNC already slows each G93 block to its axis limits (DECISIONS: the converter does not model
  dynamics).

### Weakness confirmed in our converter **[checked]**
- **Arcs centred on the chuck axis are cut as polygons.** `layout-xzc.js` linearises every arc into chords (tol/2)
  and then splits each chord. Measured (2.11.1): a full G2 circle at R10 around X0 Y0 → **127 G1 blocks**, X dips to
  9.9896 (0.0104 mm, within tolerance but a polygon); R50 → 159; R100 → 316 blocks. In polar such an arc is exact with
  X constant and only C (and Z) moving: 8 blocks of ≤ 45°, zero error, and fewer blocks run faster (LinuxCNC does not
  arc-blend rotary moves). Same reasoning as the 2.5.0 radial-line fix. Concentric faces, grooves and bores are common.
  → proposal, needs Marios's yes; golden outputs would change (explain before `--update`).
- Checked, **no bug:** C unwrap (shortest delta), G93 length formula, rapid segmentation.

## 2. Simulator ideas (priority = catches a real mistake before cutting)
Sources read: CAMotics (GPL-2+, `src/gcode/plan/SCurve.cpp`, `sim/ConicSweep.cpp`), LinuxCNC 2.9 `tp.c` (GPL-2),
Kiri:Moto `src/kiri/mode/cam/work/anim-2d.js` / `anim-3d.js` (method only), FreeCAD `PathSimulator/AppGL` (LGPL),
VERICUT AUTO-DIFF (commercial, concept), cncjs (MIT).

**Weakness [checked in code]:** `material.js` caps the grid at 300 cells — on a 220 mm part one cell ≈ 0.73 mm, far
coarser than the 0.025 mm tolerance, so the material view cannot show small gouges near the centre.

1. **Deviation colouring** (S–M, very high value): run the existing `tests/lib/replay.js` method in the page, colour
   the path green/yellow/red by distance from the CAM path, list the worst lines (click → jump).
2. **Axis speed along the path** (S, high): per G93 block the needed C (°/s), X, Z speed vs the machine's limits;
   colour where the controller will have to slow down, using the closest-approach rule above. Display only.
3. **Realistic cycle time** (M, high): trapezoid per block limited by each joint's speed/acceleration; show a range
   (exact stop … half blend). LinuxCNC 2.9 `tp.c` gives segments with rotary motion no blend arc / no tangent merge
   (parabolic G64 blend may still apply — STATUS wording to be corrected).
4. **Holder / collet collision on the height map** (S–M): a cylinder above the tool tip vs material height; chuck jaws
   as a fixed volume. Tool length from `tool.tbl` (already read by the tilt layout).
5. **Mirror aid** (S): arrow + text "C+ = chuck clockwise seen from the cutter" and a small "F" on the stock in both
   views, for comparing the animation with the real air cut. (Software still cannot prove a part is not mirrored.)
6. **Finer, tool-shaped height map** (M): worker + Float32 grid ≈ 0.1 mm, ball/V tool profiles (Kiri method).
7. GPU height map (M–L), true 3D dexel/implicit material (L, only for the tilt layout) — later.
8. Playback: link output line ↔ animation both ways, step ±1 block, jump to next tool change/warning (S);
   click-to-measure radius/angle/Z (S); **report export** (S) — cycle time range, peak C, rapids in material, worst
   deviation, tools, version, settings (also the record the Kiri author will ask for).
Not worth it: gcode-preview, gcode.ws (printer viewers), bCNC (same as 8), NC Corrector (closed), vismach (no material).

## 3. LinuxCNC on Debian 13 "trixie"
- **Version:** latest stable **2.9.10** (tag `v2.9.10`, debian/changelog 2026-07-02). 2.10 is **not released**
  (master `2.10.0~pre2`). Debian's own trixie archive carries **2.9.4** *(snippet)*; the LinuxCNC repo
  (`deb http://linuxcnc.org trixie base`) carries the newer builds. Default LinuxCNC ISO is trixie since 2.9.8 *(snippet)*.
- **Real-time:** kernel `linux-image-rt-amd64` (PREEMPT_RT is mainline since 6.12, trixie runs 6.12); package
  `linuxcnc-uspace`; check `uname -v` shows PREEMPT_RT. **Use 2.9.9 or newer:** 2.9.9 removed the old
  `/sys/kernel/realtime` check that made older builds fall back to non-real-time on 6.12 kernels.
  Run `latency-histogram` / `latency-test` (with a Mesa Ethernet card the servo thread is what matters).
- **Mesa 7i92 (hm2_eth):** PC static e.g. 10.10.10.1, board 10.10.10.10; in `/etc/network/interfaces`
  `hardware-irq-coalesce-rx-usecs 0` (needs `ethtool`). If NetworkManager manages the port, that line may be ignored —
  mark the port unmanaged or set it with `nmcli` (not verified). Check with `ethtool -c <if>`.
  hm2_eth 2.9.10 isolates traffic only with **`iptables`**; on a pure-nftables trixie it warns "Unable to restrict other
  access" and continues without isolation → install `iptables`.
- **2.9 → 2.10 (only if he ever upgrades):** `[JOINT_n]/[AXIS_x]`, trivkins XZC, G93, halui unchanged; optional new keys
  (S-curve `PLANNER_TYPE`, jerk, `G64_DEFAULT_TOLERANCE`); preview needs OpenGL 3.3; "new HAL API, all pins 64-bit"
  (effect on the gamepad nets not checked). **Advice: stay on 2.9.x.**
- **G93:** unchanged; each block takes 1/F min unless the axis limits make it longer; F required on every G1/G2/G3; no
  minimum block time, no limit on F digits in the interpreter.
- **Line length — verified in the LinuxCNC 2.9.10 source by Claude:** `interp_read.cc` `Interp::read_text` reads with
  `fgets(raw_line, LINELEN, …)` (`LINELEN` 255, `src/emc/linuxcnc.h`) and fails with **"Command too long"** when the
  line *including its line ending* reaches 254 characters. ⇒ at most **252 characters** of text with LF endings,
  **251** with Windows CR LF. **[checked]** our converter passed a 302-character CAM comment through unchanged.
- **To verify on his machine:** `[TRAJ] MAX_ANGULAR_VELOCITY` is documented only under `[DISPLAY]` — may be ignored in
  `[TRAJ]` (the delivered `.ini` has it in both; harmless if ignored, but must be checked against the docs).

## 4. The polar setting inside a CAM — updated
- **FreeCAD main (`dd5f963`, 2026-10-11) now has a real machine definition** (`src/Mod/CAM/Machine/models/machine.py`,
  Billy Huddleston / sliptonic, since 2026-03): linear + rotary axes, kinematic chain, `.fcm` JSON files, a post-processor
  name and properties per machine. `Kinematics.rotation_strategy` has a **`POST_TRANSFORM`** value ("the post rotates
  every coordinate") — declared, not implemented: exactly the slot for our polar transform. No XZC/polar template, no G93
  (an XZC machine would show as "custom").
- **Posts and machines can be shipped as an Addon** (Addon Manager) without core changes: `<Postprocessor>` and
  `<machine>` content types (2026-04 / 2026-03). A post subclasses `PostProcessor` (`Path/Post/Processor.py`) and gets
  real `Path.Command` objects; hook `_expand_postprocessor_commands`, settings via `get_property_schema`.
  An addon that only subclasses FreeCAD's LGPL classes can stay MIT. FreeCAD's simulator reads XYZ only (no C).
  Calling our JavaScript from the post (node subprocess) is possible but fragile → a **Python port** with the golden
  tests as the shared specification is the clean way.
- **Kiri:Moto:** active work is on branch `rel-next` (`76d509f`, 4.7.4, 2026-10-04), not `master`. Licence unchanged
  (MIT file + "All Rights Reserved" headers). `gcodeProc` hook still works (`src/kiri/app/export.js`, device `code.proc`)
  but only in the UI export dialog, no UI field, self-hosted only; no kinematics/plugin API, no G93.
  *(Corrections to the sub-report: our `convert()` already returns text, and Kiri's `; tool#= flute=` comments are
  already read since 2.5.0.)*
- **Recommendation (changed since 2026-10-08, now with evidence):**
  - Now: the page as it is ("post from any CAM, convert").
  - Long term, **FreeCAD addon "Polar XZC"**: `.fcm` machine files (XZC, XZC+B) + a polar post (Python port of the core,
    MIT) — needs nobody's permission. Start only after the F cut and an aluminium part prove the method.
    Questions for FreeCAD (sliptonic / Billy Huddleston): accept non-XYZ chains (X, Z, C) in `machine_type`; an official
    `POST_TRANSFORM` hook; G93 in posts; rotary axes in CAM Sim.
  - Kiri stays possible but depends entirely on its single author; contact him only after real tests and photos.

### Bugs found and confirmed by Claude (fix prepared in a scratch copy, waiting for Marios's yes)
1. **Merge of short moves (< 0.15 mm), any machine, both cutting sides:**
   - a 0.1 mm Z step followed by an XY move became one ramp: step up → **0.1 mm gouge**, plunge → 0.1 mm left uncut
     (the merge check looked at XY only);
   - the merged point was written at the **next line's feed** (F100 plunge at F1000; F50 at F3000).
   Fix: points carry Z (3-D check) and are never merged across a feed change; a waiting point is written at its own feed.
2. **"Both sides" (Signed-X) only:** a Signed-X move shorter than 0.15 mm was still waiting when the return to the pole
   was decided → one block swung X through 0 while C turned 159°: **0.12 mm off** (random sweep: 275/3000 cases over
   0.026 mm, worst 0.18). Fix: write the waiting move first → 9/3000, worst 0.0268 (same as one-side).
3. Messages: "using Pocket Fill" printed when no fill is done → now "converted point by point, no fill"; header showed
   centre zone "0.01" for 0.0125.
4. Line length: comments shortened so no output line exceeds 251 characters; a code line that is still too long stops
   the conversion; lint checks it.
Result in the scratch copy: all tests (input 77), sweeps unchanged, golden 144/144 changed **in the header comment
only** (centre-zone number).
